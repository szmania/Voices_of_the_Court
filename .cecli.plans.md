# Plan to Optimize Battle Report Log Parsing

## 1. Project Overview
This plan addresses a performance issue in the battle report feature introduced in Pull Request #9 by "Lisiyuan233". The current implementation reads the entire `debug.log` file to parse battle data, which is inefficient and can lead to slow performance and potential errors with large log files.

**Objective**: Optimize the log parsing in `BattleReportGenerator.ts` to improve performance and reliability.

## 2. Changes Made by Lisiyuan233

### Battle Report Feature
- **Trigger**: `VOTC:BATTLE_REPORT` clipboard signal.
- **Core Logic**: `src/main/battleReport/BattleReportGenerator.ts`
- **UI**: `public/configWindow/battleReport.html` and `src/configWindow/battleReportRenderer.ts`
- **Prompts & Localization**: Added `battleReportPrompt` and localization keys for 11 languages.

### Checkpoint (Save-Rollback Sync) Feature
- **Core Logic**: Uses a `votc_checkpoint_epoch` integer from the `VOTC:IN` log line (`data[9]`) to filter "future" data when an older save is loaded.
- **Affected Files**: `GameData.ts`, `summaryManager.ts`, `conversationHistory.ts`, `Conversation.ts`, `LetterManager.ts`, `DiaryManager.ts`, and related interfaces.

## 3. Issue Analysis
The function `extractBattleReportData` in `src/main/battleReport/BattleReportGenerator.ts` reads the entire `debug.log` file using `fs.readFileSync`. This is highly inefficient, especially as the log file grows. The application's performance will degrade over time, and it may even crash if the log file becomes too large for memory.

## 4. Implementation Steps
- [ ] **Modify `extractBattleReportData`**:
    - **File**: `src/main/battleReport/BattleReportGenerator.ts`
    - **Change**: Replace `fs.readFileSync` with a more efficient method that reads the file from the end, similar to the `readLastRelevantBlock` function in `src/shared/gameData/parseLog.ts`. This will involve:
        - Opening the file using `fs.promises.open`.
        - Reading the file in chunks from the end.
        - Searching for the `VOTC:BATTLE_REPORT` blocks within those chunks.
        - Parsing the relevant data from the identified blocks.

## 5. Verification Steps
- [ ] **Confirm Functionality**: After implementing the change, trigger a battle in the game to generate a battle report.
- [ ] **Verify Report Generation**: Check that the `battle_reportN.txt` file is created correctly in the `run` folder.
- [ ] **Check for Errors**: Monitor the application logs for any errors related to log parsing or battle report generation.
- [ ] **Performance**: (Optional) Compare the time taken to generate a battle report before and after the change, especially with a large `debug.log` file.
